## 一、要解决什么（动机）

主楼 AI 对「时间流逝后事物应有的状态」缺乏计算能力。两个真实例子：

1. **伤口**：一周前割伤了手，理论上一周后该愈合了，但模型反复说手很痛、伤没好、甚至化脓。它不会算「距受伤已过 7 天 → 该结痂/愈合」。
2. **月经**：每月一次。模型要么把「一个月前来的」当成昨天，要么以为一直没来，算不出上次经期和下次经期的关系。

共性 = 模型**记得事件、但算不出事件距今多久、也推不出该呈现什么状态**。

目标：用【历】做一层「暗账」——AI 从正文里**捞取**事件、**打点**（此时此刻·此物此状态）、每 N 楼**重算时间差并更新现状**、最后以**强提醒**格式注入主楼 AI，让主楼只负责「表达已被嚼碎的结论」。

## 二、核心设计决策（8 条骨架，均已对齐）

1. **地基 = 时间差**。一次性事件 vs 周期事件，**不是两种数据类型**，而是「了结时**丢弃** vs **滚动到下一轮**」的结算方式差异。字段通用，只结算逻辑分叉。

2. **锚 = 底账（冷·入库即钉死）+ 活账（热·每次捞取时 AI 更新现状）**。
   - 底账：起始锚（受伤那楼 + 当时历日期）、事由、类型——**永不改**。
   - 活账：现状、现状锚（最近一次判定的楼层+历日期）——**每轮判定车上刷新**。

3. **共用【历】的「今天」做时间基准，但独立存储**。【历】的 `almTodayAnchor()`（`{month,day}`）是全插件权威「今天」，点/线/面都查它；暗账也查它算时间差，但数据**不塞进历、不塞 chat_metadata 顶层**，新开一个 key。

4. **检索 = 结构化筛选网优先，向量是后期锦上添花**。用户明确：先把自己的检索库和检索机制建起来（标签/人物/时间到期/状态筛选），**向量是后期召回增强，不是地基**。很多记忆插件都是先正常检索再加向量。

5. **状态更新搭【历】现成的 N 楼判定车，零额外成本**。每次判定：构画 AI 读活跃池 + 最近若干楼 → **只输出被改动的条目**。每次更新 → toast「N 条被改·请注意查看」（走通知三档）+ 被改条目**置顶/加粗** + 存 before→after，**用户可否决**。

6. **用户编辑即锁死 AI**（照点/线的锁机制）。用户手动改过的条目，AI 判定车不许再动。

7. **打点宁滥勿缺**。多记几条的成本 << 漏记导致滚雪球的成本。捞取时倾向多记。

8. **砍掉「暂态偏离」特殊类型**。失温/中暑这类不做专门类型——靠通用的「现状随时间衰减」+「早期就抓住」覆盖。（用户原话：如果一个状态在最开始就被抓住，一般不会演变到失控；我举的失控例子是滚雪球特例。）

## 三、通用字段 schema（一套字段管所有类型）

```
{
  id,                         // 唯一
  事由,                       // "割伤左手" / "和小美约吃饭" / "月经"
  类型,                       // 持续状态 | 约定待办 | 周期
  牵扯: [人物],               // 涉及谁（user / char名 / NPC）
  标签: [关键词],             // 检索用：#伤 #左手 #身体
  起始锚: { 楼层, 历日期 },   // 底账·钉死
  现状,                       // "已结痂，轻微刺痛" —— 活账·每轮可刷
  现状锚: { 楼层, 历日期 },   // 活账·最近一次判定的时空
  周期长度,                   // 仅「周期」：30（天）
  到期锚: { 历日期 },         // 仅「约定/周期」：下次该发生的历日期
  状态,                       // 活跃 | 已了结
  锁,                         // 无 | 用户锁
}
```

- **全通用**，只有 `周期长度` / `到期锚` 是类型特有的可选字段。
- 新字段一律**追加末尾 + 可选**，别插中间（照 feedback_gouhua_jian_injection_spec：格式在多处各存一份，插中间会静默错位）。

三类结算差异：
| 类型 | 例子 | 时间差算什么 | 了结时 |
|------|------|------------|--------|
| 持续状态 | 伤口/怀孕/情绪 | 距起始锚多久 → 推现状 | 愈合即置「已了结」（丢弃） |
| 约定待办 | 哪天去吃饭 | 距到期锚还有/超了多久 | 兑现或取消即了结（丢弃） |
| 周期 | 月经/发薪 | 距上次 + 距下次 | 到期即**滚动**到期锚 += 周期长度（不丢） |

## 四、三段提示词（互相耦合 · 倒着写的参考方向）

三段是一条链：① 打点入库 → ② N 楼判定刷现状 → ③ 注入主楼。倒着设计是因为**先确定注入要什么，才知道判定要算什么，才知道打点要存什么**。

### ③ 注入（depth 浅层 1~2，SYSTEM role）
- **构画 AI 已经把状态嚼碎**，主楼 AI 只负责「表达这个结论」，不让它自己算。
- 放**浅层**是硬约束（用户原话：深层 AI 读不到就彻底废了）。现有 lines/outline 是 depth=4；暗账要更浅（1~2），因为它是「最重要的时间锚」。**但别到 depth 0**，会盖住用户最新 input。
- 分两组呈现：
  - **正在持续的身心状态**：每条带「距今 X 天 + 所以现在应该怎样」。例：`割伤左手 · 距今 7 天 · 应已结痂愈合、勿再描述剧痛化脓`。
  - **临近的约定与周期**：例：`月经 · 距上次 28 天 · 预计 2 天后来潮`；`和小美约饭 · 已约定但未定档 · 可择机推动兑现`。

### ② 判定（搭 N 楼车 · 构画 AI）
- 构画 AI 读**活跃池 + 最近 N 楼**，**只输出被改动的条目**（`<update id=.. 现状=.. 状态=..>` 之类，省 token）。
- 规则：
  - 按**剧情实况**判，不是按模板套天数（愈合快慢看剧情）。
  - **持续状态随时间衰减**：默认往「趋于平复/愈合」走，除非剧情明确恶化。
  - **约定/周期到期即结算**：兑现→了结；周期到期→滚动到期锚。
  - **不碰用户锁条目**。

### ① 打点（拾贝 · 构画 AI）
- 从最近若干楼**捞取**新事件（海边拾贝式），**宁可多记**。
- 填：事由 | 类型 | 牵扯 | 标签 | 现状 | （到期锚或周期长度，若适用）。
- **已在池里的跳过**（靠标签/事由去重）。

> 用户 2026-08-07 说提示词部分「暂时想不到需要增补的」——即此三段已覆盖当前想到的全部。

## 五、存储决策

- **新开 `sp-ledger` 这个 chat_metadata key**，加进 `OWN_KEYS` 白名单（当前是 `['sp-store','sp-memory','sp-theater']`）。
- **单一池子**：了结的条目只翻 `状态=已了结` 标志位、**筛选时默认排除**，**不物理删除**（用户可捞回）。
- 落盘走 `saveMetadata()` 同步写（避开 2.6.1「clearChat 取消防抖」丢数据的坑）+ 批量落盘。
- **物理体积可忽略**：一条锚约 300~500 字节，500 条 ≈ 150~250KB，相对动辄数 MB 的 chat 文件微不足道。
- **接进「存储管理」面板**：`storeTotalBytes()` / `clearOwnKey()` 已存在 → 显示暗账占用 + 提供手动清理归档池，几乎零成本。用户明确要这个（「构画现在做的存储管理非常好，让我知道占了多少空间」）。

## 六、几个已澄清的边界（防止明天重踩）

- **谁算状态 = 构画 AI，不是主楼 AI**。理由（用户洞察，推翻了我最初的偏向）：主楼 AI 要读上下文+记忆+世界书+人设+用户 input，注意力涣散；构画 AI 读得少、相对客观。**所以数据库里要存「应达到的状态/现状」这条**——因为推演在我们这边做。
- **同名不同次事件靠时间锚区分**：一年前 char 受过伤、昨天又受伤 = 两条独立锚，起始锚不同，AI 不会混成同一个伤口。
- **「哪天去吃个饭」也要记**：没有具体日期的约定同样入库（类型=约定待办，到期锚留空/待定）——它是真约定，只是没定档。这个例子证伪了我之前「有时间指向的先做、纯悬念的后做」的错误切法。改用比喻：**闹钟（到点自己响 = 时间检索）vs 门铃（上下文命中才响 = 语义检索）**，两者都要。

**关键旋钮 / 事实**（下次排查先看这些）
